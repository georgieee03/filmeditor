# Music discovery and soundtrack integration

Reviewed on 2026-10-08. This records primary-source research and implementation review requirements for the requested music workflow. Network availability below is an observation from this Mac, not a provider uptime guarantee.

## Source selection

Use [Openverse's audio API](https://api.openverse.org/v1/) for anonymous discovery, then download an explicitly selected result into the project. Its [live schema](https://api.openverse.org/v1/schema/?format=json) exposes search, license filters, result details, and provider statistics. Search queries are limited to 200 characters. Duration metadata is in milliseconds. License-filter results must still be checked locally before import. Keep searches small and honor HTTP 429 and response rate-limit headers; the [official client documentation](https://docs.openverse.org/packages/js/api_client/index.html) notes that backoff is the caller's responsibility.

The live [audio provider listing](https://api.openverse.org/v1/audio/stats/) currently includes Jamendo, Freesound, and Wikimedia Commons. Bounded probes against one returned URL from each provider returned HTTP 206 and valid MP3 or Ogg file signatures. These probes read only 64 bytes; they do not establish complete download or decoding.

A later end-to-end anonymous import separately downloaded and fully decoded [Ambient Dance by Zeropage](https://www.jamendo.com/track/23557): 5,618,636 bytes and 228.74907 seconds, carrying [CC BY 3.0](https://creativecommons.org/licenses/by/3.0/) provider metadata. Source, attribution, exact terms, and the read-only original were retained in the temporary project. The test left no song in the source repository. This establishes one working full-song provider path; Freesound and Wikimedia remain limited to the earlier bounded probes.

The sampled `category=music` search returned Jamendo tracks. Suitable Freesound and Wikimedia items can have no category; a strict music-category filter narrows the catalog. Do not present pronunciations, podcasts, or every sound effect as a song. Free Music Archive was absent from the current provider listing; its [license guide](https://freemusicarchive.org/License_Guide) also describes differing per-track permissions, so it is not a universal free-use fallback.

## Licensing and attribution

Default discovery and automatic import to `cc0`, `pdm`, and `by`. [CC BY 4.0](https://creativecommons.org/licenses/by/4.0/) permits adaptations with attribution, a license link, and identification of changes. Retain title, artist, source page, exact license/version/link, supplied attribution, acquisition time, and the imported asset identity. Include a copyable credit that records trimming, looping, fades, or other modifications when applicable. Preserve notices supplied by the source.

[CC0 and the Public Domain Mark](https://creativecommons.org/public-domain/) serve different purposes: CC0 is a rights waiver; PDM identifies material believed to be in the public domain. Keep provenance for both. Exclude NC, ND, SA, and unfamiliar licenses from the automatic default. The [CC BY-ND legal code](https://creativecommons.org/licenses/by-nd/4.0/legalcode.en) explicitly treats synchronizing music to moving images as adapted material, which ND does not permit sharing under that license.

[Openverse's terms](https://docs.openverse.org/terms_of_service.html) require respecting provider terms and attribution, honoring access limits, and identifying the integration as using Openverse without endorsement. The catalog does not independently verify licensing. Show source and license details; do not describe a search result as guaranteed copyright clearance. Do not scrape entire catalogs or bypass authentication, rate limits, or unavailable downloads.

## Editing behavior

The ordinary soundtrack action should add music to a dedicated audio track, fit the selected sequence range with trimming or explicit looping, set gain, and apply start/end fades. Preserve the visual edit and existing audio. Return the exact placed range and changes so Codex can explain the result. Put the operation in the existing revision-checked edit and undo transaction; a network download or analysis must not make an earlier revision valid again.

Editing picture to beats is a separate, explicit action. A lightweight energy/onset/autocorrelation estimate is a guide, not a calibrated musical-confidence probability. Silence, ambient material, tempo changes, and half/double-tempo ambiguity need honest unknown or low-confidence outcomes. The [primary beat-tracking research by Ellis](https://www.ee.columbia.edu/~dpwe/pubs/Ellis07-beattrack.pdf) discusses the assumptions and limits of deriving beat locations from onset strength and estimated tempo. Report the analyzed span and avoid extrapolating a short analysis across an unmeasured song. Fixed gain is not automatic dialogue ducking; that term requires a measured envelope or a real side-chain process such as the one described in [FFmpeg's audio filter documentation](https://ffmpeg.org/ffmpeg-filters.html#sidechaincompress).

## Download and validation boundary

Fetch through the backend and preview the imported local asset through the existing signed media route. Treat catalog titles, attribution text, URLs, and tags as untrusted data. Accept a catalog identifier, re-fetch its detail from the fixed API origin, and re-check the permitted license. Do not expose arbitrary URL fetching through the music tool.

Require HTTPS, reject credentials in URLs and private/reserved network destinations, validate each redirect, and connect to the validated public address with the original TLS hostname. This avoids validating one DNS answer and connecting to a different one. Bound response size, connection/read duration, redirects, concurrent downloads, decoder threads, and analysis duration. System DNS resolution remains a blocking operating-system call; the connection/read watchdog is not an absolute bound on DNS latency. A byte cap must apply even when Content-Length is absent or wrong. Validate audio before publishing it as an asset and remove partial files on failure or cancellation. Restrict decoder input [protocols](https://ffmpeg.org/ffmpeg-protocols.html#Protocol-Options) and [demuxers](https://ffmpeg.org/ffmpeg-formats.html#Format-Options), so a renamed playlist cannot make the decoder fetch embedded network or local-file references outside the downloader's checks.

Acceptance must distinguish mocked network tests from actual provider access. Cover malformed metadata, license changes, failed/oversized/truncated downloads, redirect-to-private-host rejection, stale revisions, lock handling, exact trim/loop duration, undo, and low-confidence analysis. Render a short video with a soundtrack through actual MLT, decode the whole output, and check the resulting audio rather than relying only on an audio-stream flag. Keep third-party test downloads and generated media outside tracked source.

## Implemented behavior and review evidence

`film/music.py` exposes search, catalog import, local analysis, and revision-safe fitting through the shared MCP registry. The native Music dialog supports local song import, catalog discovery, source details, gain, source offset, overall fades, optional looping, and estimated beat markers. The catalog text is inserted as text, not executable markup. Codex instructions prefer existing imported audio, use the same tools, preserve picture/dialogue, and report provenance. Downloads are serialized per workspace, capped at 256 MiB, restricted to public HTTPS destinations, and decoded with protocol/demuxer allowlists. Fitting is bounded to one hour, analysis to ten minutes, and timeline beat markers to 64.

Review corrections included known license-version validation, preserving official license URLs, retaining committed soundtrack files when later registration or undo persistence fails, a shared deadline across resolved addresses/TLS, rejection of deadline-induced partial EOF, and retaining the socket while a `Connection: close` HTTP response is still being read. The actual provider request exposed the last issue; a standard-library HTTP/socketpair regression now covers it. Source-offset fitting resets audio timestamps before applying fades so the requested offset cannot silently consume the fade-in.

Sixteen independent tests in `tests/test_music_review.py` pass, including real local socket ownership and mocked network/engine failure cases. Credits are generated for known music resources in the immutable render XML through shared `start_render` forwarding, so manual and Codex exports use the same path. Retired bin assets retain attribution; unrelated imported music is excluded; sidecar failure leaves the already-started render visible with a warning. The UI offers the exported `.credits.txt` for saving.

Actual synthetic-media acceptance verifies an eight-second soundtrack from an offset, exact frame/sample duration, global fade envelopes, original-source preservation, unchanged existing picture/dialogue, one shared undo step, and a fully decoded MLT export. A two-second interior interval contains both the 220 Hz synthetic song and the 440 Hz dialogue tone, confirming the soundtrack was actually mixed into the export. Installed WKWebView acceptance separately verifies local-song fitting and persistence after reopen. These checks do not establish arbitrary-song beat accuracy, seamless loop joins, automatic dialogue ducking, final-mix quality, real camera fidelity, or long-film stability.

The browser workflow also passed actual local-song file input, fitting through the Music dialog, fully decoded export, revision-scoped export credits, reload persistence, and zero JavaScript errors. A separate mocked catalog result confirmed HTML-looking titles/attribution remain inert. That mocked catalog check is distinct from the real anonymous provider download above.
